# Validation and release prerequisites

Automated verification uses Go tests, synthetic provider responses, local HTTP servers, and isolated temporary installation directories. No real provider token, scanner, corporate instance, OS Keychain, or real LaunchAgent is used by tests.

| Behavior | Direct verification |
| --- | --- |
| Successful imports and native lifecycle/severity | Provider/store tests for GitHub and GitLab, terminal states, scanner metadata, analysis streams and change comparisons |
| Genuine zero versus unavailable/denied/unknown | Null/empty/API-error/schema-gap fixtures and rendered empty-state assertions |
| Disabled scanners and missing analysis | Exact GitHub message fixtures, ambiguous 403/404 kept as failures, expired/rate-limited responses take precedence, bounded/redacted error bodies, prior findings/evidence retained, and no same-slot retries for coverage gaps |
| Activity details and history | Persisted repository/category/status/reason per run, later successful imports and renames preserve history, escaped content, distinct counters, explicit legacy summaries, and exact run ordering/retention across fractional seconds and timezone offsets |
| GitLab without introspection | Null/blocked schema metadata with successful paginated reads, secret-title redaction and lifecycle preservation, optional scanner evidence, genuine empty reports, rejected/partial/null reports, missing pagination metadata, and no fallback after denied credentials or rate limits |
| Credentials, pagination, rate limits | Auth headers, safe redirects, same-origin links, pagination loops, retries/cancellation, expired/denied tokens and persisted manual/scheduled deadlines across daily slots/restarts and edited schedules; manual refresh preserves the scheduled attempt budget; optional GitLab scanner-query limits retain complete findings and the deadline; explicit restored-credential revalidation |
| Transport failures | Timeout and certificate verification failures produce distinct, actionable messages; nested transport URLs, credentials and certificate details remain redacted |
| Interrupted/partial refresh | Transaction rollback, retained findings/evidence, interrupted run recovery, overlap coalescing |
| Renames, archives and selections | Stable provider IDs and concurrent selection preservation; deselected repositories retain active findings in explicit detail/filter views while staying out of portfolio totals and refreshes; discovery rejects stale results/status after credential replacement/removal |

Baseline checks: `make check` selects Go 1.26.9 and runs uncached race tests, golangci-lint, vet, tidy/module verification, govulncheck and browser checksums. `make commit-check` checks the isolated index export. The initial candidate also requires independent Codex and Codex Security reviews with real results; see [testing](testing.md). Hosted CI and PR review remain unexecuted until an authorized push/PR exists. Verify that the module minimum is 1.26.9, older compilers reject it with automatic toolchain switching disabled, and `go mod tidy -diff` reports no changes. Confirm the selected SQLite/libc pair remains v1.60.1/v1.77.1 when updating other dependencies. Browser asset digests are checked against `scripts/browser-assets.sha256`. Build with CGO disabled for macOS and Linux, arm64 and amd64. Release packaging is exercised locally and must contain only the executable, source, documentation, and license notices. Check each generated `THIRD_PARTY_LICENSES.txt` against that binary's target and dependency metadata, including nested Go/browser notices and exclusion of test/compiler components. Missing notices must stop packaging; generated notices must stay out of the index. The source archive retains dependency source/license metadata through vendoring. Verify the compiler in each executable with `go version -m`; direct Go commands and IDE builds must select the pinned toolchain too.

Tests establish implemented semantics, not live provider compatibility for every edition/version. Before a stable release:

1. Validate public/private GitHub repositories and organization approval/permissions with user-provided read-only connections, including secret-pattern availability and optional default setup metadata.
2. Validate the exact self-managed GitLab version, introspection, custom roles, license/features, scanner configuration, categories, and lifecycle behavior. Unknown timestamps must remain unknown.
3. Exercise real Keychain/Secret Service authorization and login/start/wake/update/stop behavior on target hosts, with no corporate data in public evidence.
4. Rehearse restore from a private disposable backup and verify corporate-data permission before any cross-host migration.
5. Review staged files, corresponding-source archives, dependency/license/vulnerability results, and GitHub metadata before first publication/tagging.

Local execution evidence is kept under ignored `output/` with source-tree identities because this initial workspace has no Git HEAD/review base. The application preview uses the proposed bootstrap tree as its comparison base, without creating a commit. Verify bootstrap README/LICENSE bytes, links and secret scan separately; application tests are not applicable to that tree. Trace the approval/publication sequence in [GitHub validation](github-validation.md) manually and label hosted actions, CodeQL, AI integration and rule enforcement unexecuted until authorized. Local evidence is not a substitute for live provider acceptance or hosted review results.
