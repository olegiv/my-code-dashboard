# Architecture

The executable owns one installation directory, one SQLite database, one in-process scheduler, and one loopback HTTP server. A file lock prevents two processes from refreshing the same installation. All HTML, plain CSS, HTMX 4, Alpine CSP, and first-party JavaScript are embedded with `go:embed`. Go's `html/template`, `net/http`, cross-origin protection, and timezone database handle the web boundary. No browser asset is fetched remotely.

HTMX 4 uses `includeIndicatorCSS: false` because indicator styling belongs to the embedded CSS. Its obsolete `allowEval` setting is not a security control in this version; the response CSP forbids string evaluation and inline scripts. Application expression attributes are fixed source strings, and provider values remain escaped data. Alpine uses its CSP-compatible parser.

`model` holds normalized records and their native lifecycle/severity fields. `provider` exposes `Validate`, `Discover`, `RefreshRepository`, and `Collect`; integrations are typed, allowlisted HTTP readers rather than broad provider SDKs. `secret` supplies system keyring or provisioned-file credentials. `store` owns transactional SQLite snapshots. `engine` coordinates collection and scheduling. `platform` owns locking, backups, and native service files. `web` renders escaped templates and handles GUI forms. The CLI assembles them.

## Persistence

SQLite uses the pure-Go `modernc.org/sqlite` driver with WAL, foreign keys, a busy timeout, one writer connection, private permissions, and schema versioning. There is no CGO/system SQLite dependency. Main tables are settings, connections, repositories, coverage, findings, refresh runs, and change events. Credentials never enter these tables.

Repository identity is provider + canonical base URL + immutable provider numeric ID; names, paths, namespaces, default branches, and archive state can change. Identity comparison folds hostname case and removes the default HTTPS port 443, preserving installation subpaths and nondefault ports. Discovery reuses an existing record's ID, including an older noncanonical ID, so bookmarks, findings, coverage and history remain attached. It preserves monitoring selections. Refresh updates metadata without overwriting a concurrent GUI selection. A selected repository discovered through multiple credentials keeps its existing connection; reconnect/update that connection to replace its credential. Saved connection URLs and credential-recipient validation are unchanged.

If multiple legacy records already represent the same instance and numeric ID, discovery fails atomically rather than choosing a credential or merging conflicting histories. This prevents further changes but does not reconcile duplicates already stored; see [operations](operations.md#provider-connection-troubleshooting).

Both adapters require a positive numeric ID and nonempty repository path before accepting metadata. Refresh also requires the returned ID to match the requested immutable ID; discovery rejects an incomplete list rather than saving partial results. The store independently rejects metadata updates that change the indexed external ID. Rejected updates retain the previous repository, findings and activity identity, with collection health reporting the error. Valid renames and archive changes still update the same record, and subsequent backups retain consistent identities.

Connection credential writes/removal, discovery commits and refresh writes share a mutex. Discovery captures an in-memory credential generation before provider requests, releases the mutex for network work, and discards both results and status updates if credentials changed meanwhile. Its final status write rereads current metadata. Refresh binds each cached adapter to the current connection generation and checks it before saving repository metadata or category snapshots. A reconnect/removal discards outstanding results for that connection, preserves previous complete findings and coverage, and records an explicit failure reason in activity. Later repositories on that stale adapter are skipped; other connections continue. Provider network requests never hold this mutex. A subsequent refresh uses the current credential. Generations only coordinate in-flight work within one process; the installation lock prevents a second process from writing the same database.

Each category commits atomically after complete pagination. Failed/unavailable categories update health and attempt time, retaining last success, prior findings, and prior analysis evidence. Complete responses upsert native states and compare with the preceding successful snapshot. Missing records are labelled missing and retain their prior state, including open counts. Initial successful imports create a baseline without a change storm. Changes retain 90 days by default; refresh logs retain 30 days. Findings remain until the installation is removed; no destructive GUI purge exists.

Refresh runs store category outcomes with the repository ID/name, provider, collection status, scanner state, and a sanitized reason. Outcomes are checkpointed after each repository and retained with their run, so later imports or renames do not rewrite history. Existing run records without outcomes are labeled as legacy summaries rather than reconstructed from current coverage. JSON record additions require no SQLite schema migration.

The UI fills every absent category with an unknown-coverage placeholder, including when an interrupted first import already committed some categories. Existing category status, timestamps and findings stay intact; a partial first import cannot appear fully collected merely because its coverage list is nonempty. Placeholders affect current portfolio/repository coverage and counts, without being persisted or inventing historical run outcomes. Paused repositories retain their category details and active findings while staying outside portfolio totals.

Settings also retain the last attempted repository ID while a portfolio refresh is incomplete. The next manual or scheduled refresh starts after that repository in the current selection and wraps around. A completed traversal clears the cursor. Removed or deselected cursor IDs fall back to ordinary name order; each installation keeps its own progress in SQLite. Progress is saved between repositories, not within a provider page or category. A crash before a checkpoint can repeat the current repository. A checkpoint write failure stops the run with a partial result while retaining completed imports.

Backup import is a separate trust boundary. Before querying application tables, the read-only validator disables trusted-schema behavior and compares every SQLite schema object and nullable SQL definition with a private in-memory database built from the application's schema. Physical root pages are irrelevant; triggers, views, altered constraints/indexes and other noncanonical objects are rejected. Connection keys and serialized records must be SQLite TEXT, with nonempty keys and unique decoded IDs that exactly match their relational keys. Validation uses the same Go JSON decoder as runtime consumers, including escaped and case-insensitive field representations. This prevents shadow records from escaping quarantine through a different SQLite storage class or decoded identity. Existing archive, version, settings, integrity and foreign-key checks remain in force. Validation finishes before destination backup or replacement; the extracted candidate stays in the private restore directory. Same-user filesystem tampering remains outside the security boundary.

Every imported connection must independently name a supported provider and pass the live adapter's HTTPS target rules, including connections with no repositories. GitHub uses the canonical GitHub.com base; GitLab permits configured installation paths and ports. Optional empty repository/finding links cannot bypass connection validation. Invalid targets are rejected before replacement, preventing them from blocking later discovery through another connection. Browser and headless reconnect compare the saved and submitted targets after the same HTTPS URL validation, so accepted surrounding whitespace or a trailing slash cannot strand an imported connection in quarantine. The browser trims whitespace from the URL supplied to its reconnect form without rewriting stored connection data. Provider, host, port and installation-path recipient checks still apply.

Every repository, coverage, finding, run and change row is also decoded as its application type before replacement. Decoded identities, repository references, selection flags, indexed finding fields and timestamps must match their native SQLite columns. This rejects empty objects and effective JSON field aliases that disagree with relational keys, which would otherwise make reads and updates address different records. Change IDs are allocated by SQLite after serialization, so only their duplicated repository and timestamp fields are compared. Malformed JSON, null records, incompatible field types and non-text records are rejected too. The validator streams all rows, including history beyond the UI's read limits, without rebuilding the database through capped queries.

Saving a monitoring selection rereads current repository metadata inside the write transaction and serializes the whole typed record. This preserves concurrent refresh metadata and removes duplicate or case-aliased JSON members from accepted imported records, so an old alias cannot override a later deselection. Repository reads, subsequent refresh selection and future backups agree with the saved choice.

Unselected repositories remain excluded from portfolio totals and refreshes. Their detail page and explicit repository filter still show retained active findings, with monitoring shown as paused on the detail page. Run ordering and retention compare timestamps as whole Unix seconds and integer nanoseconds, including existing offset-bearing records; variable-length RFC3339 fractions are not ordered as text.

Filtering and pagination within Findings return an HTMX fragment for ordinary HTMX requests. Pagination from Overview or repository details instead uses a full navigation to Findings, preserving the active/repository scope while loading its heading, navigation and filter controls. HTMX history restoration also receives the complete shell, since its body replacement must restore navigation and filter controls along with results. Response variation includes both HTMX request headers, and all application responses remain `no-store`.

Successful restore retains the destination credential namespace, marks every imported connection reconnection-required and keeps all records/history without replaying truncated UI queries. The engine rejects those connections before reading any credential backend until explicit successful revalidation. Rejection leaves the destination intact. See [backup operations](operations.md#backup-and-restore).

Connection discovery and credential removal use fixed POST routes. Connection IDs are escaped hidden form values and are read from the POST body, so imported identifiers cannot change a form's route or introduce query parameters. Host, cross-origin and CSRF checks apply to both operations.

Selecting an existing connection fills the form with its saved provider, URL and name, updates the token guidance, and clears any entered token. The selector includes the saved URL so imported names cannot conceal the recipient. Changing the provider or URL also clears the token. Before validation, the server requires the submitted provider and normalized URL to match the saved connection; a mismatch is rejected without calling the provider or accessing its credential backend. This check also protects submissions when JavaScript is unavailable.

Coverage separates collection outcome, scanner evidence, last attempt/success, and any provider analysis timestamp/ref/commit. An analysis timestamp always refers to provider evidence, never the synchronization time. GitHub's displayed analysis timestamp is the oldest latest successful tool/category stream, with its matching commit; warnings/errors and default-setup state are noted. GitLab scanner enablement is independent of vulnerability report access. Persistent GitLab vulnerabilities do not supply a reliable per-scanner analysis timestamp here.

GitLab instances that hide schema introspection can still expose vulnerability reports. The adapter verifies a minimal fixed read-only query with explicit lifecycle states and cursor pagination against that instance. Required report data and pagination metadata must be present on every page; errors or null data never become a successful empty import. Optional scanner evidence is read separately and otherwise stays unknown. This fallback needs no provider configuration or token-scope changes.

Enabled GitLab scanner types are compared with latest-pipeline run types before grouping categories. One successful scanner cannot hide another enabled scanner's missing run. That category remains enabled with a coverage gap naming the missing types, while complete findings still import. The gap reaches portfolio and repository summaries and saved refresh outcomes independently of report access.

## Scheduling and failure handling

The default calendar slot is 09:00 Europe/Zurich. Slots use local calendar arithmetic and persist as UTC instants. On startup and once per minute, the scheduler checks the latest due slot. A missed sequence of days produces one latest-slot catch-up. A successful slot is consumed; a failed one permits at most three attempts, with five/ten minute backoff and any later provider rate-limit deadline. Persisted attempts survive restart, and outstanding provider deadlines survive daily slot changes, including after the final attempt; an interrupted run is labelled interrupted on the next start. Manual and scheduled refreshes share one mutex; overlapping requests coalesce.

For custom times inside a DST gap, the slot moves forward by the timezone's offset change (02:30 becomes 03:30 for a one-hour gap). A repeated clock time uses its earlier occurrence once. Previous dates are reconstructed with the configured hour/minute, so gap normalization cannot replay a consumed prior slot. The default 09:00 Zurich slot is unaffected by these transition-hour cases.

Provider deadlines observed during a manual refresh are persisted too. Manual refresh does not consume the scheduled attempt budget; the next scheduled collection, including after restart, a new daily slot, or schedule preference changes, waits for the latest saved deadline. Changing the time or timezone resets the slot and attempt budget while retaining outstanding backoff. A rate limit encountered by GitLab's optional scanner-metadata query retains the complete vulnerability import, leaves scanner evidence unknown, and propagates the retry deadline through coverage into persisted schedule state.

Disabled scanners, missing analysis, and unsupported category sources are counted separately from failures. They retain prior evidence and do not schedule same-slot retries. A refresh with coverage gaps has a distinct result; permission, ambiguous availability, network, response, and storage failures still produce a partial result and use the retry budget. Successful report access and disabled scanner metadata can coexist, as with GitLab historical vulnerabilities.

Provider requests have 30-second timeouts, up to three attempts for transport/5xx failures, cancellation, safe same-origin redirects, and bounded responses. A refresh has a 30-minute budget. REST/GraphQL pagination is bounded to 1,000 pages and 100,000 records per category/project; exceeding bounds is a visible failure rather than partial success. HTTP 401/403/404, GraphQL errors/null data, schema gaps, and rate limits remain distinct from zero findings. A provider adapter suppresses further requests until an observed rate-limit deadline. Discovery is all-or-nothing for a returned repository list; it does not delete previously known inaccessible repositories.

HTTP 403 with `Retry-After` is treated as a secondary rate limit even when the primary remaining count is nonzero. Its deadline follows the same suppression and persisted scheduling path as HTTP 429 or an exhausted primary limit; ordinary permission-denied 403 responses retain their denied status.

## Practical scale and limitations

Designed initially for up to roughly 500 selected repositories and 100,000 retained findings per installation. UI aggregation groups records by repository and paginates finding display in batches of 50, but still reads retained findings into memory. These are design targets, not benchmarked guarantees. Collection is sequential to simplify limits and avoid bursts. Persisted repository progress prevents every time-limited refresh from restarting at the same portfolio prefix; it does not guarantee that one large repository fits the refresh budget.

There is no application authentication, cross-installation sync, scanner execution, webhook receiver, remote notifications, raw response archive, or server deployment automation. macOS/Linux are the distribution targets. V1 supports trusted single-user machines only: other local accounts and processes can read the loopback dashboard and download backups. Authentication is deferred and remains required before shared-host or internet-facing deployment; HTTPS and corporate-data permission are additional prerequisites for server migration.
